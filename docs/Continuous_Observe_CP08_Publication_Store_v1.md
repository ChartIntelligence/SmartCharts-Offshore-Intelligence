This is a **trusted local ingestion boundary**. A digest proves byte consistency, not authentic producer execution. A trusted evaluation callback must honestly consume the supplied evidence and produce the declared results; tracing a supplied artifact cannot prove its internal scientific use. A malicious callback or compromised trusted worker can fabricate a self-consistent submission. SQL does not execute JavaScript science or certify its execution. There is no public client submission route. Operational reuse still requires retained-source scientific adapter equivalence under the pre-existing publication governance; this mission does not claim a running scheduled publisher or production readiness.

## PostgreSQL state and revision semantics

`cp08.contexts` is immutable and registered only with migration authority. `cp08.versions` stores immutable exact envelope text, byte digest, cycle/context/revision identity, parent, action, lifecycle and scientific state. `cp08.heads` identifies one authoritative revision per cycle/context. Worker has no direct access to any of these tables.

`cp08.submit(text)` locks the registered context, checks local isolation, context/time/version identity, digest and result/lifecycle consistency, compares expected parent/revision, then atomically inserts a version and moves the head. Exact retries return the retained version without moving an older head back. Same identity/different bytes and competing revisions fail closed. Pending writes are invisible until commit. Rollback removes both version and head; lost ACK recovery first queries authoritative state, then may retry identical bytes.

`ORIGINAL` starts revision 1. `STATUS` records lifecycle progress for a nonfinal attempt. Once completed or withdrawn, status updates cannot replace it: a completed `CORRECTION` or explicit `WITHDRAWAL` is required. Both append with the current parent and next revision. A withdrawn head cannot appear as active; replaying an earlier version cannot reactivate it. A later explicit correction is a new lineage action, not implicit resurrection.

`cp08.lookup(text,timestamptz,text)` separates exact cycle from successful history. The read adapter labels history explicitly and reports current-cycle lifecycle separately. Failed/delayed/missing current cycles never silently borrow an older successful cycle. The existing observation acceptance/fencing transaction, evidence immutability and recovery procedures are unchanged.

## Privilege surface

Existing restricted worker `pelora_cp02_worker` receives only schema USAGE and EXECUTE on `cp08.submit(text)` and `cp08.lookup(text,timestamp with time zone,text)` for CP-08. All new tables and other functions deny worker/PUBLIC access. Both routines belong to nonlogin `pelora_cp02_owner`, use `search_path=pg_catalog` and qualified application objects, and have no dynamic SQL. Worker cannot register contexts, alter routines, own objects, mutate immutable records, update heads directly, create schemas/tables or use database TEMP/admin rights. `publicationPrivilegeManifest.v1.json` extends the existing manifests with exact bodies, objects and triggers. Platform catalog/session/advisory-lock privileges remain ordinary PostgreSQL privileges, not application table mutation rights.
